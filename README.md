# SQL-аналитика интернет-магазина

Учебный проект на SQL (SQLite): 7 аналитических задач по данным интернет-магазина и 7 задач по оптимизации запросов.
В задачах используются CTE, оконные функции, подзапросы, индексы и анализ планов выполнения.

## Возможности

- Сегментирует пользователей по числу оплаченных заказов и считает LTV каждого сегмента.
- Ранжирует товары внутри категории по месячной выручке и отбирает топ-3.
- Находит пользователей, которые смотрели категорию, но не покупали в ней, и аномально крупные заказы.
- Считает продуктовые метрики: эффективность промокодов, repeat-rate по городам, активацию за первые 7 дней.
- Ускоряет медленные запросы индексами и переписыванием SQL (папка `optimization/`).

## Аналитика: задачи и результаты

Данные — синтетический интернет-магазин за 2024 год: 700 пользователей, 80 товаров, 2 600 заказов, 9 499 событий (папка `tables/`).

| Файл | Задача | Главный результат |
|---|---|---|
| `LTV_segments.sql` | LTV по сегментам пользователей | 34% клиентов с 4+ заказами приносят 57% выручки |
| `top_3.sql` | Топ-3 товара в категории по месячной выручке | Рейтинг за 13 месяцев по 6 категориям |
| `look_not_paid.sql` | Смотрели категорию, но не покупали | 755 пар «пользователь — категория» у 442 пользователей |
| `promo.sql` | Промокоды: заказы, выручка, средний чек | WELCOME10 — больше всего заказов, SUMMER15 — самый высокий средний чек |
| `repeat_rate.sql` | Города с repeat-rate выше среднего | Новосибирск (88,5%), Санкт-Петербург, Москва при среднем 83,4% |
| `7d_activ.sql` | Активация за первые 7 дней по каналам | Лучший канал — email (15,9%), худший — organic (9,1%) |
| `overprice_order.sql` | Заказы в 3+ раза крупнее среднего у покупателя | 140 таких заказов у 127 пользователей |

Полный результат каждой задачи лежит рядом с запросом в файле `<имя>.csv`.

## Оптимизация: выводы

| Файл | Что сделано | Время до → после |
|---|---|---|
| `month_filter.sql` | `substr(order_date, ...)` заменён на диапазон дат, добавлен индекс `(status, order_date)` | 8,8 → 0,6 мс (~15×) |
| `dashboard_index.sql` | Составной индекс `(status, order_date, user_id)` | 23,6 → 5,4 мс (~4×) |
| `preaggregation.sql` | `order_items` агрегируется до уровня заказа перед `JOIN` | 173 → 159 мс (~8%) |
| `not_exists_index.sql` | Индекс `(user_id, event_type)` для коррелированного `NOT EXISTS` | ~14 мс; без индекса запрос просматривает все события для каждого пользователя |
| `latest_events.sql` | Индекс `(user_id, event_time)` вместо отдельной сортировки | 19,4 → 0,8 мс (~24×) |
| `distinct_to_exists.sql` | `DISTINCT` после `JOIN` заменён на `EXISTS` | Из плана ушла временная таблица для `DISTINCT` |
| `index_budget.sql` | 3 индекса под 3 частых запроса | Все три запроса идут через поиск по индексу |

Что из этого следует:

- **Функция над колонкой в `WHERE` отключает индекс.** Тот же фильтр, записанный диапазоном значений, использует индекс.
- **Порядок колонок в составном индексе важен:** сначала колонка с условием равенства, потом диапазон, потом группировка.
- **Индекс может заменить сортировку:** с индексом `(user_id, event_time)` запрос `ORDER BY ... LIMIT` читает уже упорядоченные данные.
- **Коррелированному подзапросу нужен индекс по ключу связи**, иначе он заново просматривает таблицу для каждой строки.
- **`EXISTS` убирает дубли без `DISTINCT`**, но на больших данных ему тоже нужны индексы.
- **Индекс ускоряет чтение, но замедляет запись и занимает место**, поэтому создавать их стоит под самые частые запросы.

Замеры сделаны на отдельном, более крупном наборе данных (12 000 пользователей, 65 000 заказов, 180 000 событий). В репозиторий он не входит.

## Требования

- SQLite CLI (`sqlite3`) 3.33+. На macOS он уже установлен, на Ubuntu/Debian ставится командой `sudo apt install sqlite3`.
- Git.

## Установка

1. Скачайте репозиторий и перейдите в его папку:

```bash
git clone https://github.com/48dmggtsg4-ops/SQL_project.git
```

```bash
cd SQL_project
```

2. Соберите базу `shop.db` из CSV-файлов:

```bash
sqlite3 shop.db <<'EOF'
CREATE TABLE users (user_id INTEGER, signup_date TEXT, signup_channel TEXT, city TEXT);
CREATE TABLE products (product_id INTEGER, category TEXT, brand TEXT, base_price REAL);
CREATE TABLE orders (order_id INTEGER, user_id INTEGER, order_date TEXT, status TEXT, promo_code TEXT);
CREATE TABLE order_items (order_id INTEGER, product_id INTEGER, quantity INTEGER, price REAL);
CREATE TABLE events (event_id INTEGER, user_id INTEGER, event_time TEXT, event_type TEXT, product_id INTEGER);
.import --csv --skip 1 tables/users.csv users
.import --csv --skip 1 tables/products.csv products
.import --csv --skip 1 tables/orders.csv orders
.import --csv --skip 1 tables/order_items.csv order_items
.import --csv --skip 1 tables/events.csv events
UPDATE orders SET promo_code = NULL WHERE promo_code = '';
EOF
```

## Использование

Запустите любую аналитическую задачу, например промокоды:

```bash
sqlite3 -box shop.db < promo.sql
```
